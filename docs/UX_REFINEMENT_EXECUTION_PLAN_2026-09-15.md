# K-Tour ID · 전체 여정 UX 개선 실행안

작성: 2026-09-15 · 아래는 승인 당시 계획이며 조사 기준은 `5c2a62a` 공개 목업이다. 이후 실행·합의·검수·보류 상태는 [실행 기록](./ux-refinement/2026-09-15/README.md)과 [릴리스 기록](./ux-refinement/2026-09-15/RELEASE.md)을 따른다.

이번 사전 조사는 세 역할의 독립적인 코드·문서 검토다. 전체 브라우저 여정 완주, 세 UX 평가자의 최종 디자인 합의, 이미지 권리 확보 또는 개선 구현을 완료했다는 뜻이 아니다. 이미 전달한 Telegram 문구는 삭제하며 개발 인계서는 유지한다.

## 1. 목표와 범위

- 탐색이 먼저인 모바일 웹앱. K-Tour ID 흑백 브랜드, 온도 중심 지도와 음식 콘텐츠를 유지한다.
- 화면·시트·단계·예외·복귀까지 목록화하고, 불필요한 선택과 중복 설명을 줄인다.
- 매장 → 혜택/주문 → 필요한 자격 → 부족분 충전 → 결제 → 내역 → 같은 매장 여정을 자연스럽게 연결한다.
- 모든 기존 기능은 `유지 / 화면 통합 / 노출 위치 이동 / 삭제 제안`으로 분류한다. 실제 기능 삭제는 문서 충돌·사용자 가치·실패 경로를 검토한 뒤 결정한다.
- 실제 CX/OpenDID/OmniOne Chain/Sui 연동은 기존 개발자의 해커톤 범위다. 실제 금융·예약은 이번 해커톤 필수 실연동에 포함하지 않고 기존 목업으로 유지한다. 이번 UX 작업은 해당 연결 지점을 보존하며 목업과 개발 요구사항을 일치시킨다. Sumsub 실험은 별도다.

우선순위: 최신 사용자 결정 → [Deployment Spec §1.1](./DEPLOYMENT_SPEC.md#11-문서-우선순위)와 [Sui 추가 명세](./HACKATHON_SUI_REQUIRED_ADDENDUM_2026-09-14.md) → 현재 배포 코드·실행 증거 → 과거 PRD. 구현에 없다는 이유로 요구사항을 없애지 않고, 옛 PRD에 있다는 이유로 폐기된 UX를 복원하지 않는다.

## 3. 리소스 운용

동시 작업 한도는 **총 4개: 조정자 1 + 작업 에이전트 3**다. 모든 역할을 항상 동시에 띄우지 않고 단계별로 교대한다.

| 단계 | 작업 슬롯 A | 작업 슬롯 B | 작업 슬롯 C | 조정자 |
|---|---|---|---|---|
| 목록화 | 코드 기반 전체 여정 지도 | 브라우저 기반 독립 전체 여정 지도 | 이미지 빈칸·콘텐츠 후보 조사 | PRD 대조·누락/충돌 관리 |
| 의사결정 | UX 평가자: 발견·첫 진입·정보 구조 | UX 평가자: 거래·신뢰·오류 복구 | UX 평가자: 시각·모션·접근성 | PRD 보호 검토·합의 기록 |
| 구현 | 승인된 여정 1묶음 | 충돌하지 않는 콘텐츠/여정 1묶음 | 비작성자 반례 검수 | 공통 파일 소유·통합·문서 동기화 |
| 최종 검수 | 처음부터 끝까지 새 방문자 검수 | 실패·중복·복귀 집중 검수 | 시각·사진·언어·성능 검수 | 변경 내역과 검수 증거 대조·배포 판정 |

- 동일 화면의 작성자가 자기 변경의 최종 검수자가 되지 않는다. 구현자 둘과 독립 검수자 하나를 기본으로 유지한다.
- 파일 목록 추출, 승인된 번역·스키마 정규화, 이미지 메타데이터 목록화 등 반복 작업은 Luna로 할당할 수 있다. 자격·금액·상태 병합과 PRD 해석은 판단 담당이 검토한다.
- 이 세션에는 Sonnet이 제공되지 않는다. 사용 가능한 모델로 역할을 구성하며 Sonnet 검수를 했다고 표시하지 않는다.
- 공통 token/CSS, 앱 셸, 상태 모델, schema는 각각 단일 작성자만 수정한다. 지역별 콘텐츠·독립 컴포넌트는 병렬 처리한다.
- 각 작업은 기준 SHA, 소유 파일, 입력/완료 조건, 검사 명령을 갖는 작은 묶음으로 배정한다. 워크트리·브라우저 저장소·포트를 분리한다. 빌드 stage와 pixel snapshot은 여러 작업이 동시에 재생성하지 않는다.
- main/Harvey는 개발 시작점으로 보존한다. 본 UX 구현은 별도 브랜치와 Preview에서 진행하고, 개발자의 새 커밋과 충돌 여부를 확인한 뒤 검수된 변경만 반영한다. 강제 push하지 않는다.
- 진행 기록은 묶음별 `미착수 / 조사 / 결정 대기 / 구현 / 검수 / 완료`로 남긴다. 중단 시 마지막 SHA·재현 경로·다음 행동에서 재개한다.

## 4. 단계별 진행과 통과 조건

### A. 두 개의 독립 sitemap을 만들고 교차 반박

첫 목록을 작성할 때 두 에이전트는 상대 목록을 보지 않는다. 이후 서로 상대가 누락한 진입점·예외·복귀를 찾아낸다.

**한 행의 단위:** `flowId / surfaceId / step / state / entry / precondition / action / mutation / next / cancel·back·reload return / PRD ID / source / browser evidence / status`.

탭·전체 페이지뿐 아니라 bottom sheet, modal, drawer, 준비 중, 빈 결과, 접근 불가, 만료, unknown, 취소, 재시도, 외부 앱 복귀, 중단 후 재개도 포함한다. 기존 FL·G·MW ID와 연결하고 같은 상태의 중복 진입은 edge로 관리한다. 테스트 편의용 direct state와 일반 사용자가 도달 가능한 화면을 구별한다.

코드에서 발견했지만 브라우저에서 도달 못한 항목은 성공으로 세지 않고 `미도달 / 필요 요구 미구현 / historical-only / 내부 전용`으로 근거를 남긴다. 브라우저가 놓친 조건 분기는 코드 담당이 재현 조건을 제공한다. PRD 필수 기능이 양쪽 목록에 없어도 누락으로 기록한다.

**Gate A:** 범위 내 각 기능의 상태·이동·복귀가 식별되고, 두 목록의 모든 차이와 PRD 누락에 판정·근거·담당을 지정한다. 해당 묶음의 P0·필수 요구 누락은 해결 계획을 승인하거나 묶음 전체를 명시적으로 보류하기 전까지 구현 승인하지 않는다. 보류를 완료로 집계하지 않는다. 전 조합을 무한히 열거하는 대신 상태 전이와 위험 조합을 명시한다. 기능 여정 수·이미지 필요 수·변경 예상량은 여기서 확정한다.

### B. 세 UX 평가자의 독립 제안 → 반대 검토 → 합의

각 평가자는 먼저 다른 평가자의 답을 보지 않고 `문제 증거 → 사용자 목적 → 대안 → 잃는 기능 → 검사법`을 작성한다.

- 점수 항목: 목적의 명확성, 불필요한 결정 수, 맥락 유지, 잘못된 이해 위험, 오류 복구, 시각 일관성, 접근성.
- 숫자는 우선순위 비교 보조다. 평가 점수만으로 실제 사용성이나 100% 완성도를 증명하지 않는다.
- 채택 조건: 세 UX 역할의 명시적 합의 + PRD 검토의 미해결 차단 사항 없음.
- 단순 다수결로 동의·금액 확인·연령·Payment KYC·취소·복구를 삭제하지 않는다.
- 반례 검토 → 수정안 재평가를 최대 2회 수행한다. 해소되지 않는 가치 충돌, 핵심 기능 삭제, 해커톤 범위 변경은 사용자에게 선택지와 영향만 짧게 질문하고 해당 묶음만 보류한다.
- 의사결정 원장은 `유지 / 통합 / 이동 / 삭제 제안`, before/after step, 보존 상태, 동의/반대 이유, 검증 결과를 기록한다.

### C. 통일된 시각 기준과 대표 화면 3개

**주 레퍼런스는 Toss의 일관된 컴포넌트·계층·접근성 접근**으로 제안한다. 같은 컴포넌트가 서비스마다 달라지는 문제를 공통 규칙으로 다룬다는 점을 적용한다. K-Tour ID 흑백 브랜드와 지도 온도색은 유지하며 Toss 자산·상표·내부 UI kit를 복제하지 않는다. [Toss 공식 디자인 시스템 글](https://toss.tech/article/toss-design-system)

Revolut은 두 번째 비주얼 테마가 아니라 익숙한 사용자 용어, 모듈 재사용, 근거 기반 검증이라는 검토 원칙의 보조 참고로만 사용한다. [Revolut 공식 디자인 원칙](https://www.revolut.com/blog/post/our-top-5-design-principles-at-revolut/)

먼저 **도시 지도 / 매장 상세 / 충전·결제**를 동일 기준으로 시안화해 비교한다. 이후 전체 화면에 적용한다. 타이포·숫자/통화·간격·둥근 모서리·그림자·버튼 높이·상태색·사진 비율·sheet header/footer·stepper·오류/영수증·motion token을 공통화한다.

미감은 완전히 객관적인 항목이 아니다. 따라서 스타일 선택과 측정 가능한 품질을 구별한다. 주요 조작은 44px 터치 영역을 프로젝트 목표로 삼고, WCAG 2.2 AA의 최소 target/spacing 규칙도 확인한다. 일반 텍스트 4.5:1, 큰 텍스트 3:1 대비를 검사한다. 확대·키보드·focus·reduced-motion 대응을 별도로 검사한다. [Target size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html), [Contrast](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html), [Motion](https://www.w3.org/WAI/WCAG22/Understanding/animation-from-interactions.html)

**Gate C:** 대표 화면 3종과 실패/긴 문구 변형이 합의 기준을 만족한 뒤 전면 적용한다. 페이지 수만큼 각각 다른 스타일을 만들지 않는다.

### D. 흐름 개선 — 먼저 검증할 제안

1. **첫 진입:** 즉시 지도 탐색을 유지한다. 선택형 취향 설정은 목적·지역·취향을 반복해서 묻는지 실제 단계 수로 측정하고, 필요한 경우 한 시트로 압축한다. 설정 미완료·저장 실패도 탐색을 막지 않는다. 위치 권한은 ‘내 주변’을 요청할 때만 설명한다.
2. **지도 → 장소:** 지원하는 매장에 한해 peek에서도 혜택/주문 등 주요 행동 1개를 발견하게 하는 안을 검토한다. 길찾기는 보조. 상세와 목록은 같은 매장·사진·온도·서비스 상태를 표현한다.
3. **거래 여정:** 잔액 충분/부족 경로를 분리하고, 부족할 때 같은 주문 안에서 충전 후 돌아온다. 주문·매장·금액·혜택을 다시 선택시키지 않는다. 충전 완료가 곧 구매 승인이라는 의미는 아니다.
4. **스테이블코인:** 일반 가격·잔액은 KRW. ooKRW 설명은 hover뿐 아니라 모바일 탭·키보드로도 열 수 있다. 사용자가 스테이블코인 충전을 선택한 분기에서는 자산·network·전환 금액·수수료·서명 내용을 숨기지 않는다. 같은 지갑/자산 연결을 반복 요구하는지 확인한다.
5. **중복 정리:** ID·Wallet, My Korea, 주문/환불 내역과 매장 내 내역의 진입점은 용도가 다를 수 있다. 같은 원장과 상세 화면을 재사용하되 출발 맥락은 보존한다. Tables 동행 계획과 실제 매장 예약, 충전과 구매, 승인과 체결, 결제와 방문 증거를 합치지 않는다.
6. **필요한 자격:** 이미 충족된 항목은 반복 설명하지 않고 필요한 것만 요청한다. Person·Age·Payment·서비스 혜택 자격은 별도 상태로 유지하고, 목적/대상/금액 변경 시 재동의가 필요한 경우를 보존한다.

새로고침 시 주문·잔액의 현재 보존 범위도 별도 점검한다. 현 commerceSession은 실제 금융 원장이 아니며 초기화 경로가 있으므로, ‘공통 상태를 쓴다’는 이유만으로 새로고침 복원이 완료됐다고 판단하지 않는다. 복원이 필요하면 명시적인 샘플 세션/작업 계약을 설계하고, 충전 이력을 다시 읽는 동작으로 돈을 중복 생성하지 않는다. 일반 USD 참고액과 코인 견적의 예시 환산 기준 차이도 동일 금액 표시 정책에서 설명한다.

측정은 임의의 ‘무조건 3탭’이 아니라 대표 작업별 시작→목적 달성의 action 수, 중복 입력 수, 주문 맥락 손실, 필수 동의 보존을 before/after로 비교한다.

### E. 콘텐츠·실제 이미지·지도 생동감 — 병렬 묶음

**콘텐츠:** 1차는 기존 추천 24곳의 사진 빈칸과 설명부터 보강한다. 새 장소 후보는 서울·부산·제주별 4곳씩 소규모로 조사하고, 검증·사진 이용권·좌표·중복 검사를 통과한 만큼만 수록한다. 수량을 맞추기 위해 불확실한 장소를 넣지 않는다. 새 도시는 기존 도시 UX 안정 후 별도 후보로 제안한다.

**사진 슬롯:** 지도 peek, 추천 카드, 목록 thumbnail, 상세 hero/gallery, 메뉴/혜택 카드, 주문·영수증의 매장 식별 사진을 조사한다. 신원 동의·법적 설명·단순 상태 화면에 장식 사진을 강제로 넣지는 않는다.

- 이미지 검색·연결된 자료 도구로 찾되 URL 존재와 이용 허락은 다르다. 출처 URL·권리/허락·크레딧·확인일·매장/메뉴 일치·crop/alt·배포 파일을 asset manifest에 저장한다.
- 출처가 없는 지도/리뷰 사이트 이미지를 무단 hotlink하거나, 다른 식당 사진·AI 이미지를 실제 매장/실제 여행자 증거처럼 쓰지 않는다.
- 권리를 확보하지 못한 곳은 미확보로 남긴다. 허용된 분류 예시 이미지가 필요할 때만 imagegen skill/tool로 생성하고 실제 사진과 분리한다. 이미지 작업은 시각 규칙 확정 후 제한된 batch로 실행한다.
- 장소 단위로 ID·도시·좌표·다국어명·출처·확인일·사진 권리·서비스 capability를 검증한다. 조사 목록과 공식 목록의 중복은 원 출처 ID와 기존 저장·주문·예약·복귀 참조를 보존하고, 검증된 alias/canonical 매핑으로 표시만 통합한다. 기존 ID를 삭제하거나 조사 장소를 canonical 매장으로 임의 변환하지 않는다.

**생동감:** 별도의 임의 애니메이션들을 늘리지 않고 하나의 event/frame 모델이 지도 온도, 선택 매장 추세, 최신 활동 표시, 사진/리스트에 같은 변화를 전파하도록 한다. 2.5D 건물은 배경으로 두고 온도 변화가 주목되도록 한다. 새 활동은 작은 강조·타임라인·점진적 변화로 보여주고 사용 중 자동 재정렬/지도 이동으로 탭 대상을 바꾸지 않는다.

샘플 재생과 로컬 작성, 검증된 실제 집계를 구별한다. 실제 수집 API가 없는 상태에서는 가짜 ‘방금 실제 여행자가 방문’ 알림을 만들지 않는다. 토큰 구매·사진 선택·DID 확인도 방문으로 집계하지 않는다. reduced motion, 화면 밖/백그라운드 정지, 지도 조작 중 완화, 타일 실패 fallback을 보존한다.

### F. 변경마다 비작성자 adversarial 검수 → 통합 회귀

- 필수 반례: 취소·뒤로/앞으로·닫기·새로고침·외부 앱 복귀·다른 장소 전환·중복 탭·저장 차단·키보드·이미지 실패·타일 실패·오프라인·quote 만료·잔액 부족·결과 unknown·중복 결제/환불.
- 제출 전 취소는 무변경이다. 이미 승인·전송·처리 중인 작업의 닫기/뒤로가기는 업무 취소나 잔액 복원이 아니다. 동일 작업 ID·pending/unknown·보류 금액과 상태 재확인 경로를 유지한다. 중복 동작은 한 작업, unknown은 실패/성공으로 단정하지 않음, 복귀는 원 매장·검색·카메라·목록 스크롤·focus를 복원한다.
- 코인 출발 확인만으로 잔액을 올리지 않는다. 충전 완료 뒤 구매는 별도 결제 동의를 받아야 하며, 충전 중 견적이 만료되면 새 견적을 확인·재동의한다.
- 모든 상태는 우선 기준 모바일/언어에서 실제 도달과 전이를 검수한다. 3도시·EN/KO/JA·light/dark/system·After 19 독립·320/360/390/430·tablet/desktop·짧은 높이/가로모드는 위험 기반 조합으로 확장한다. 금융/자격/복귀 핵심 경로는 축소하지 않는다.
- 전체 조합 Cartesian product나 테스트 파일 수를 완료율로 쓰지 않는다. `상태 도달 / 전이 / PRD 보존 / 시각 / 데이터·자산 / 운영 URL`의 별도 coverage를 남긴다. skip과 미실행은 PASS가 아니다.
- 각 묶음 관련 검사 → 통합 후보 전체 계약/typecheck/build → 독립 E2E/시각 검수 → Preview → 승인된 운영 배포 → 같은 배포의 smoke 순서다. snapshot은 검수 없이 일괄 갱신하지 않는다.
- 실제 iOS Safari/Android 조작 검수가 필요하나 접근이 없으면 emulator 결과와 구분해 사용자에게 짧은 확인 경로를 요청한다. 실제 기기 미검수를 숨기지 않는다.

## 5. 우선순위·검수 시간·완료 판정

권장 작업 배분은 목록/요구 대조 20%, 의사결정/공통 기준 15%, 구현·콘텐츠 40%, 독립 회귀 25%다. 추정 비율이지 고정 작업시간이나 완성도 점수가 아니다. Gate A에서 실제 변경 수와 이미지 확보량을 확인한 뒤 묶음별 예상 시간을 다시 산정한다.

1. **P0:** 여정 누락·막힘·잘못된 자격/금액·복귀 손실·상반된 현행 문서.
2. **P1:** 매장→충전→결제 연결, 첫 진입/주요 CTA, 시트/타이포/사진 위계.
3. **P2:** 검증된 콘텐츠 추가, 이벤트 기반 온도 개선, 세부 모션.

한 묶음의 완료는 승인된 before/after, PRD 보존 대조, 수정 코드, 비작성자 재현 검수, 같은 SHA 증거와 문서 동기화가 모두 있을 때다. 오픈 P0/P1은 운영 반영을 차단한다. 외부 계정·사진 권리·제품 선택이 막으면 그 묶음만 대기하고 나머지는 진행한다.

## 6. 사용자 확인과 최종 산출물

기본 제안은 Toss 중심·현재 흑백 브랜드 유지, 기존 세 도시 먼저, 실연동은 추가하지 않는 목업 개선이다. 이 기준으로 계획을 구체화하는 데 새로운 계정/키나 사용자 답변은 필수가 아니다.

바로 질문할 항목은 핵심 기능 삭제/사업 의미 변경, 합의되지 않는 정보 구조, 큰 시각 방향 변경, 비용·권리 허락·외부 계정·실기기 필요, Harvey 구현과의 계약 충돌이다. 사소한 간격/카피마다 확인받지 않는다. 한 번에 최대 1–3개의 짧은 질문으로 영향과 추천안을 제시한다.

실행 중 산출물은 하나의 여정 registry를 기준으로 sitemap·QA 작업표·문서가 연결되도록 유지한다. 비슷한 PRD/완료 보고서를 계속 새로 만들어 정본을 늘리지 않는다.

- 전체 여정 지도 + 상태/복귀 registry + 미도달/미구현 목록.
- 중복/단순화 결정 원장과 세 UX 평가·PRD 반대 검토 기록.
- 통일된 시각 token·대표 화면 및 before/after.
- 장소/사진 manifest와 검증 보류 사유.
- 변경 묶음별 독립 검수와 최종 배포 증거.
- 사용자에게는 최종 링크, 바뀐 대표 흐름, 남은 외부 의존성만 전달한다. Telegram 재전달 문구는 만들지 않는다.
