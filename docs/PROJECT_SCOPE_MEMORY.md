# K-Tour ID 프로젝트 스코프 메모리

상태: `v2.0 · 2026-08-04`

이 문서는 제품·디자인·개발·발표 과정에서 다시 논의하지 않아도 되는 결정과, 반드시 다시 결정해야 하는 기술 항목을 구분하는 프로젝트 메모리다. 구현 세부사항은 [개발 명세](./DEVELOPMENT_SPEC.md), 요구사항별 증거는 [추적표](./REQUIREMENTS_TRACEABILITY.md), 미결정 기술 선택은 [개발자 결정 목록](./DEVELOPER_DECISIONS_REQUIRED.md)을 따른다.

## 1. 지금 어느 단계인가

- 1단계인 클릭 가능한 목업 제품의 UX·UI 정리와 핵심 플로우 검증은 완료됐다.
- 지금부터는 2단계인 실제 개발 명세, 연동 계약, 상태·예외·검수 기준을 작성한다.
- 목업은 개발 명세 자체가 아니다. 개발자가 결과와 사용성을 이해하는 실행 가능한 샘플이다.
- 개발 명세를 화면 문구로 다시 밀어 넣지 않는다. 사용자는 서비스에 필요한 말만 보고, 상세 규칙은 문서·API·운영 도구에 남긴다.
- 목업의 시각 언어와 정보 우선순위는 유지하되, 목업의 localStorage·타이머·가짜 DID·가짜 영수증은 생산 구현의 근거가 아니다.

## 2. 제품의 한 문장 정의

K-Tour ID는 내국인·단기 해외 방문자·등록 외국인의 서로 다른 본인확인 결과를 민간 여행·생활 서비스 자격 VC로 표준화하고, 필요한 자격만 제시해 교통·음식·쇼핑·예약·혜택·액티비티를 이용하도록 돕는 관광 신뢰지갑이다.

핵심 폐쇄 루프는 다음과 같다.

```text
본인확인
→ K-Tour ID 발급
→ 최소정보 자격 제시
→ 서비스·혜택·결제 실행
→ 주문·환불·정산
→ 비식별 실행 증거
```

## 3. 요구사항 해석 우선순위

충돌 시 아래 순서를 따른다.

1. 제품 책임자가 최근 대화에서 확정한 결정
2. 이 스코프 메모리와 `docs/DEVELOPMENT_SPEC.md`
3. 루트 K-Tour ID 제안서와 해커톤 제출 요건
4. 현재 배포된 목업의 화면·플로우
5. 공급자 매뉴얼·샘플과 공식 기술 문서
6. 과거 문서와 `legacy-contracts`

공급자 실제 기능이 제안서 표현보다 좁으면 사실에 맞게 구현·표시하고, 범위 차이를 숨기지 않는다.

## 4. 변하지 않는 제품 결정

### 4.1 신원과 자격

- K-Tour ID는 정부 신분증, 비자, 외국인등록증, 체류 허가가 아니다.
- 내국인 모바일 신분증과 지원되는 모바일 외국인등록증 제출은 OmniOne CX 경로다.
- 단기 해외 방문자의 전자여권·얼굴·라이브니스는 별도 Passport eKYC 경로다. 이를 CX 기능이라고 부르지 않는다.
- OpenDID는 K-Tour ID VC의 발급·보관·제시·검증·상태 확인 경계다.
- 가맹점은 이름·여권번호 전체가 아니라 서비스에 필요한 predicate/claim만 요청한다.
- `LIVE`, `SANDBOX`, `SIMULATED`는 실제 공급자 영수증에 따라 표시한다. 목업을 실연동으로 표현하지 않는다.

### 4.2 사용자 경험

- 첫 가입은 `가치 설명 → 체류/여행 유형 선택 → 유형별 본인확인 → 결과 검토 → 발급` 순서다.
- 발급 직후 홈으로 진입하고, 첫 실행 가이드에서 위치 사용 여부와 핵심 사용법을 설명한다.
- 이미 가입한 사용자는 홈으로 바로 들어간다. 만료·정지·폐기 상태만 갱신/복구로 우회한다.
- 위치는 opt-in이다. 거절해도 서비스 탐색과 구매가 가능하며, 허용 시 가까운 순·배달 가능 여부·픽업점·액티비티 거리를 개선한다.
- 모바일 하단 내비게이션에서 ID와 지갑은 하나의 `ID·지갑` 진입점으로 본다. 세부 화면은 분리할 수 있으나 사용자가 두 제품으로 느끼게 하지 않는다.
- 커뮤니티는 공개 소개팅이나 무제한 DM이 아니다. K-Tour ID가 활성이고 동일 액티비티 참여가 확정된 사람끼리만 그룹 채팅이 열린다.
- 성별 비율·연애 목적을 제품 규칙으로 두지 않는다. 목적은 관심사 기반 친구 만들기다.
- 채팅에는 나가기, 차단, 신고, 긴급 도움, 재가입 규칙이 있어야 한다.

### 4.3 상업 서비스

- 교통·음식·쇼핑·예약은 별도 로고 모음 페이지가 아니라 `탐색 → 구성 → 견적 → 자격/혜택 → 동의 → 결제/요청 → 제공자 상태 → 환불/지원`의 서비스 가지로 붙는다.
- Kakao T, Uber, T-money, 배달의민족, 쿠팡이츠, Olive Young, GS25 등은 목표 연동 예시다. 계약·공식 API·샌드박스 증거 전에는 제휴로 표시하지 않는다.
- 서드파티가 K-Tour ID의 OpenDID/OpenCX 기반 API를 이용하는 확장 구조를 지향한다. 앱 안에서 모든 외부 서비스를 복제하지 않는다.
- 결제 성공과 제공자 주문 성공은 다른 상태다. 한쪽만 성공하면 재조회·보상·환불 경로가 반드시 있어야 한다.
- 혜택은 자격, 예산 출처, 적용처, 최소금액, 1회성 여부, 만료, 환불 시 복원 규칙을 가진다.
- 지갑 잔액, 바우처, 포인트, 법정화폐, 스테이블코인을 화면과 원장에서 혼동하지 않는다.

### 4.4 AI

- AI는 추천·요약·여정 제안·이상 징후 보조를 한다.
- AI가 신원확인, VC 유효성, 혜택 자격, 결제 승인, 환불의 최종 판단을 대체하지 않는다.
- 금전·자격에 영향을 주는 Agentic AI 행동은 사용자 승인, 정책 검사, 멱등성 키, 실행 영수증을 요구한다.
- 여권·생체·VC 원문·전체 DID를 모델 입력이나 외부 로그에 넣지 않는다.

## 5. 기술별 책임 경계

| 기술/도메인 | 반드시 맡는 역할 | 맡기지 않는 역할 |
|---|---|---|

| Passport eKYC | 여권 MRZ/NFC, 문서 진위, 얼굴 일치·라이브니스 | 정부 신분증·체류자격 발급 |

| K-Tour Ledger | 결제·바우처·주문·환불·정산의 canonical business state | 체인 영수증만으로 거래 상태 추정 |
| OmniOne Chain | 제안서/해커톤 트랙용 비식별 발급·사용·정산 이벤트 해시 증거 | PII·VC·결제 원문 저장, 운영 DB 대체 |

| 외부 서비스 | 배차·배달·재고·예약 등 본 서비스 운영 | K-Tour 자격·캠페인 원장 임의 변경 |

## 6. Sui 필수 스코프

Sui는 선택 아이디어가 아니라 개발 범위다. 단, 제품팀이 세부 설계를 선결하지 않는다.

### 제품팀이 고정하는 결과

- 핵심 Move package를 Sui Testnet 또는 Mainnet에 실제 배포한다.
- Generic EVM bridge가 아니라 Move를 사용한다.
- `zkLogin`, `PTB`, `Walrus`, `DeepBook` 중 2개 이상을 실제 사용자 흐름에 통합한다.
- Agentic AI가 온체인 객체 또는 권한을 소유/위임받아 정책 안에서 행동하고, 그 의사결정·실행의 provenance를 검증할 수 있는 흐름을 보여준다.
- package ID, transaction digest, explorer 링크, 재현 명령, 실패 케이스를 제출 증거로 남긴다.
- DeepSurge 등록, 공개 GitHub·README, Sui 선택 이유 1페이지 case study를 준비한다.

### 개발자가 정의하고 승인받아야 하는 것

- 사용할 Sui 핵심 기능 2개 이상과 선택 이유
- 온체인/오프체인 경계와 Sui 객체·capability·event 모델
- zkLogin의 OAuth provider, salt/prover, 복구, sponsored transaction 여부
- PTB로 묶을 명령과 원자성의 정확한 범위
- Walrus 사용 시 공개 가능 데이터, 암호화·키 관리, retention
- DeepBook 사용 시 실제 유동성/환전 필요성과 규제·실패 처리
- gas sponsor, 키 보관, 업그레이드 권한, pause/recovery, indexer/RPC
- OpenDID/OmniOne Chain과 Sui 사이의 중복 이벤트·불일치 처리
- Testnet → Mainnet 승격 조건

상세 템플릿과 검수 기준은 [Sui 연동 브리프](./SUI_INTEGRATION_BRIEF.md)를 따른다.

## 7. 외부 Audit Scope 링크의 해석

참조: <https://shardlab.notion.site/ext-audit-scope-summary-en?source=copy_link>

해당 공개 문서는 K-Tour ID나 Sui가 아니라 Maroo L1의 보안 감사 소개 문서다. 그러므로 Maroo의 Cosmos-EVM fork, OKRW, PCL precompile, gnark 회로를 K-Tour ID 필수 구현으로 복사하지 않는다.

대신 아래 감사 관점은 개발자 보안 계획에 반영한다.

- P0: 체인 핵심·거버넌스·업그레이드·통화 공급 권한
- P0: 정책 집행·attestation·agent identity/delegation
- P0: ZK 회로, nullifier/Merkle, trusted setup, 감사 공개 경계
- P2: OAuth·credential store·서명·custody·WaaS의 off-chain AppSec
- P2: RPC/mempool DoS, explorer, 운영·관찰자 권한

K-Tour ID가 Maroo/OKRW를 실제 결제 레일로 추가할 경우에만 별도 체인 어댑터와 감사 범위를 새로 승인한다. Sui 요구를 Maroo EVM 코드로 충족할 수 없다.

## 8. 하지 않는 것

- 여권만으로 국가 모바일 외국인등록증·비자·체류허가를 발급한다고 주장하지 않는다.
- 계약 없는 브랜드를 공식 파트너처럼 표시하지 않는다.
- 개인정보·여권 원문·얼굴 이미지·VC 원문·사람이 읽는 결제 설명을 공개 체인이나 Walrus에 올리지 않는다.
- 단순 NFT 발행, 지갑 연결, 로고 삽입만으로 Sui/AI 통합을 완료 처리하지 않는다.
- 광고 타기팅 키로 국적·DID를 사용하거나 비식별성이 검증되지 않은 관광객 데이터를 판매하지 않는다.
- 미사용 바우처·잔액을 약관과 법률 검토 없이 플랫폼 수익으로 귀속하지 않는다.
- `legacy-contracts`의 Solidity 실험을 생산 아키텍처나 Sui 구현으로 승계하지 않는다.

## 9. 완료의 정의

기능은 화면이 있을 때가 아니라 아래가 모두 있을 때 완료다.

1. 성공·취소·거절·만료·중복·오프라인·부분성공·복구 상태가 정의돼 있다.
2. 브라우저 mock이 아니라 서버의 canonical state와 공급자 영수증을 사용한다.
3. 동일 요청 재시도에도 돈·VC·바우처·주문이 중복 생성되지 않는다.
4. 사용자, 가맹점, 정산 원장이 같은 receipt/operation ID로 대사된다.
5. 개인정보 최소화·보관·삭제·동의 철회가 검증된다.
6. OpenCX/OpenDID/Sui/체인/결제의 실행 수준이 사실대로 표시된다.
7. 자동화 테스트, 운영 대시보드, 데모 재현 절차, 제출 증거가 함께 있다.
