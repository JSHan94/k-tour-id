# K-Tour ID / ONDO 최종 산출물과 실행 기준

상태: 2026-09-08 사용자 방향 확정 · 실행 기준 · 구현 완료 보고서 아님

## 1. 최종 산출물 세 가지

| 산출물 | 반드시 포함할 결과 | 완료 증거 |
|---|---|---|
| 모바일 웹앱 | 지도 중심 탐색, 높은 시각 완성도, 매끄러운 전환, 모든 화면의 모바일 사용성 | 배포 후보의 실제 모바일 여정, 화면 캡처와 전환 영상, 접근성·성능 결과 |
| 기능별 실행 가능한 목업 | 해커톤에서 보여줄 모든 기능의 진입→처리→결과→원 행동 복귀; 오류·취소·재시도 포함 | 기능별 시나리오, 재현 가능한 fixture, 실제 브라우저 검증 |
| 백엔드 개발 인계 | 각 목업을 실제 기능으로 바꾸기 위해 필요한 API·데이터·기술·외부 연동·운영 처리 | DEPLOYMENT_SPEC, 양방향 추적표, 별도 해커톤 연동 작업 목록 |

외부 provider 연결과 실제 자금 이동은 백엔드 개발자의 구현 작업이다. 이번 프런트 산출물은 그 연결 후 사용자 경험을 샘플 데이터로 끝까지 재현한다. 미연결 화면만 있는 기능은 목업 완료로 세지 않는다.

## 2. 최신 요구사항의 적용

- 최신 사용자 요구를 범위 판단의 최우선으로 둔다. 이전 문서의 후순위 표기로 이번 목업 범위를 축소하지 않는다.
- OpenDID, OmniOne CX, OmniOne Chain, Sui를 모두 이번 목업·인계 문서의 명시적 검토 대상으로 포함한다.
- Sui의 과거 `P2 / optional` 결정은 이번 목업·명세에서 제외하는 근거로 사용하지 않는다. 주최 측 공식 필수 여부는 별도로 원문과 대조한다.
- 지갑·충전·결제·환불·혜택·정산은 이번 데모와 백엔드 작업 정의에 포함한다.
- 기존 PRD의 요구사항 ID와 flow ID는 추적 관계를 보존한다. 화면 통합과 기능 삭제를 구분한다.
- ONDO의 지도 탐색, K-Tour ID의 신원·자격, Travel Wallet의 결제를 같은 여행 맥락으로 연결한다.
- 기존 지도·sheet·gate·상태 모델을 우선 활용한다. 공통 component와 상태 계약을 정리한 후 화면별로 확장한다.

참조: [현재 Flow Catalog](./ondo-execution/03_FLOW_CATALOG.md), [역사적 스코프 메모리](./PROJECT_SCOPE_MEMORY.md), [기존 v2.1 원문 스냅샷](./DEVELOPMENT_SPEC_v2.1_SOURCE_2026-08-11.md), [외부 체인 메모](./EXTERNAL_CHAIN_INTEROPERABILITY.md). 과거 메모의 Sui 제외/P2 결정은 이번 사용자 승인과 v3 계약으로 대체됐다.

## 3. 사용자에게 확인한 선택

사용자가 2026-09-08 답변으로 다음 방향을 확정했다.

| 선택 | 권장안 | 대안 | 상태 |
|---|---|---|---|
| 공유 링크의 첫 경험 | 샘플 인증·충전·결제를 바로 완주할 수 있는 데모; 처음 한 번 간결한 안내와 필요 시 상세 정보 | — | 승인 |
| 지도 입체감 | 미니멀 지도 + 얕은 2.5D. 건물보다 온도의 동적인 변화가 중요 | — | 승인; 건물 강조 불필요 |
| 시연의 핵심 | DID 기반 정보·자격에 따라 어떤 서비스가 허용·거절되는지 PDF·PRD와 일치하게 시연 | — | 승인; 고정 마감 날짜는 제시되지 않음 |

필요한 추가 데이터 수집은 허용됐다. 먼저 기존 신호·콘텐츠를 재사용하고, 새로운 수집은 출처·이용 조건·신선도·실제 장소 일치가 확인되는 범위에서 진행한다. 이번 실행의 우선 검증은 DID 자격과 서비스 허용/거절의 연결이다.

## 4. 시각 방향 제안

### 지도

- 발자취 레퍼런스와 연결되는 깨끗한 바탕, 알아볼 수 있는 해안선·한강·도시 경계, 정확한 좌표를 유지한다.
- 서울·부산·제주의 위치, 선택 방식, 온도 표현은 동일한 시각 규칙을 사용한다. 데이터가 없는 곳의 온도는 임의로 생성하지 않는다.
- 전국→도시→동네→장소를 같은 지도 인스턴스의 카메라 이동으로 연결한다. 화면이 바뀔 때 blank canvas나 임시 세로 도시 목록이 노출되지 않아야 한다.
- 2.5D 후보는 얕은 카메라 기울기·필요한 확대 수준의 낮은 건물·부드러운 명암으로 만든다. 검색·목록·선택 때 표적이 가려지지 않도록 시야를 정돈한다.
- 장식적 지형과 날씨 설정을 핵심 탐색 조작보다 앞세우지 않는다. 3D가 기기 성능이나 지도 읽기에 불리하면 같은 데이터의 평면 보기를 사용한다.

### 움직이는 온도

- 전국에서는 지역의 존재와 상대적인 활기를, 동네에서는 온도의 분포를, 가까이서는 실제 장소를 구분해서 보여준다.
- 새 신호가 들어온 장소에만 짧은 빛의 확산을 주고, 히트맵의 밀도·색은 이전 값에서 새 값으로 부드럽게 바뀐다.
- 데모는 시간과 장소가 정해진 재현 가능한 이벤트 시나리오를 재생한다. 실제 방문객 수나 실시간 수집으로 오인시키는 문구를 쓰지 않는다.
- 값이 변한 이유와 신호 시점은 필요할 때 여는 상세에서 확인할 수 있다. freshness·confidence·sponsorship 등 기존 의미를 보존한다.
- 무작위 전체 깜빡임, 과도한 고리, 거대한 열 덩어리가 지도와 장소를 가리지 않게 한다.
- 동작 줄이기 설정에서는 이동·발광 모션을 줄여도 동일한 정보와 기능을 사용할 수 있어야 한다. 앱이 보이지 않을 때 재생을 중지한다.

### 인증·테이블·지갑 등 나머지 화면

- 토스에서 참고할 기준은 명료한 정보 우선순위, 짧은 행동 문구, 한 화면의 주 행동, 안정적인 sheet와 입력 경험이다.
- 사진·아이콘·선택 상태·진행 결과로 설명 가능한 내용을 반복 문장으로 늘리지 않는다.
- 동의 대상, 결제 금액·환율·수수료, 취소·환불의 영향처럼 판단에 필요한 정보는 읽기 쉽게 남긴다.
- KRW/USD와 천 단위 구분을 기본으로 사용하고 OOKRW·USDT·USDC와 네트워크는 상세 정보에서 설명한다.
- 기본 light/dark 테마와 After 19 탐색 모드는 독립 상태다. After 19는 대상 장소와 accent/온도 표현을 바꾸고, 다른 화면의 테마를 암묵적으로 뒤집지 않는다.
- 한글·영문·일문, 하단 안전 영역, 키보드·짧은 높이에서 같은 우선순위를 유지한다. 아이콘만 쓰는 조작에는 접근 가능한 이름과 구분되는 선택 상태가 있어야 한다.
- 장소 사진과 콘텐츠 이미지는 이용 가능한 실제 출처를 사용한다. 일반 음식 이미지를 특정 가게의 실제 음식으로 표시하지 않는다.

## 6. 백엔드 인계와 별도 해커톤 목록

정본은 [DEPLOYMENT_SPEC v3.2](./DEPLOYMENT_SPEC.md)이다. 기존 v2.1 원문을 별도 스냅샷으로 보존하고 요구를 대조·이관했다. 운영 계약의 작성과 실제 backend 구현 완료는 다르다.

인계의 각 행은 `요구사항 ID → 사용자 행동 → 실제 목업 위치 → 성공/오류 fixture → 내부 API·schema → provider/SDK → callback/event → 상태·영수증 → 복구·검수`를 포함한다.

| 기술 | 목업에서 보여줄 결과 | 백엔드 개발 작업에 강조할 것 |
|---|---|---|
| OmniOne CX | 모바일 신분증/지원 체류증 요청, 앱·QR handoff, 결과 수신, 원 행동 복귀 | 환경·provider discovery, 요청·토큰·callback 검증, claim 정규화, 지원/미지원·만료·중복 처리 |
| Passport eKYC | OCR/NFC·얼굴·라이브니스, 결과 확인·재시도·수동검토 | 별도 provider, IdentityEvidence, 동의·업로드·retention·삭제, 결과·오류 mapping |
| OpenDID | VC 발급→holder 저장→상태 확인→VP 동의·제시→파트너 검증→복구 | issuer/schema, holder, status/revocation, nonce·domain·audience, 최소 claim, 검증 receipt |
| OmniOne Chain | 업무 event의 대기·제출·확정·실패·재시도와 연결된 비식별 영수증 | 계약·역할·제품 불변식, 중복 사용 거절, outbox·DLQ·대사, ABI/address/tx 제출 증거 |
| Sui | 일관된 제품 맥락 안의 서명/자산 처리·결과·실패 복구 | SDK·Move/transaction 역할, 네트워크·custody·가스, 최종성·receipt, 체인 간 업무 상태 대사 |
| Wallet/Payment | 충전·환전·결제·환불·가맹점 정산 | rail별 사용자 자격·quote·수수료·통화, provider callback, 원장·멱등성·보류·대사 |

Sui의 구체적인 제품 역할은 기존 zkLogin·자산·bridge 후보와 제출 조건을 대조해 확정한다. 확인되지 않은 Sui↔OmniOne bridge를 이미 지원되는 기술로 명세화하지 않는다.

별도 해커톤 작업 목록에는 기술별 `공식 요건 원문 / 공식 필수·선택·확인 필요 / 프로젝트 포함 여부 / backend task / 선행 조건 / 제출할 실제 증거 / 현재 mock 증거`를 둔다. 공식 요건 충족과 목업 완성을 별도로 판정한다.

내부 API·DB·worker·배포 구성은 기존 스택을 바탕으로 필요한 만큼 정의한다. provider가 제공해야 하는 endpoint·키·네트워크 값은 확인 상태와 담당을 기록한다.

## 7. 높은 완성도를 판단할 기준

`95%`는 주관적인 완료 선언 대신 아래 검수 기준으로 구체화한다. 핵심 기능 5% 누락을 허용하는 의미로 사용하지 않는다.

1. 모든 요구사항에 목업 위치와 백엔드 작업이 연결되고, 미추적 기능·눌러도 끝나지 않는 핵심 CTA가 없다.
2. 시연에 필요한 성공 경로와 해당 기능의 주요 실패·취소·만료·재시도·복귀를 실제 브라우저에서 재현한다.
3. 360/390/430px 모바일 폭과 320px 좁은 폭, 짧은 높이·가로·키보드에서 주요 조작이 잘리거나 겹치지 않는다.
4. KO/EN/JA와 light/dark × After 19 조합에서 글자·아이콘·배경 대비와 위치가 유지된다.
5. 지도 전환은 화면 녹화로 확인하고, 첫 로딩·뒤로 가기·연속 클릭·재진입에서도 blank flash·marker 튀기·카메라 초기화가 없다.
6. 중급 모바일 기기에서 전환·드래그의 프레임과 초기 로딩을 측정한다. 3D 후보가 조작 반응을 떨어뜨리면 시각 복잡도를 줄인다.
7. 지도·인증·지갑·테이블의 대표 장면을 같은 실제 viewport에서 레퍼런스와 대조한다. 정적 문자열 테스트만으로 디자인을 통과시키지 않는다.
8. 단계별 반례 검수에서 발견된 치명적·높은 우선순위 문제를 해결하고 재현 결과를 기록한다.
9. 최종 공유 URL에서 같은 build와 fixture로 전체 여정을 재검수한다.
