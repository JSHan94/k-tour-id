## Findings

### SLEEK-R3-D3-001 — Connect async outcomes are visual-only status messages

**Severity:** `S2`
**WCAG:** `4.1.3 Status Messages (AA)`
**Flows/checkpoints:** `FL-003 ERROR/RETRY`, `FL-012 ERROR/TERMINAL`
**Code:** `k-tour-id-app/features/ondo/connect/connect-overlays.tsx:186`, `:572`–`:575`; presentation-only primitive at `k-tour-id-app/features/ondo/shared/ui/sheet.tsx:148`–`:150`

**Reproduction**

1. Seed an active, person-verified account and open a Table with `?scenario=table-network`.
2. Activate `Join preview` and wait for `TFR-NETWORK`.
3. Inspect `A connection problem interrupted the request.` and the active element.
4. Separately open Local Signal with `?scenario=local-signal-fail`, enter a draft, submit, and wait for `data-signal-status="failed"`.
5. Inspect `The signal could not be submitted. Your draft was kept.` and the focused retry control.

**Observed evidence**

- The Table message and every ancestor up to the dialog have `role=null`, `aria-live=null`, and no description relationship. Focus falls to `BODY` when the requesting button is replaced.
- The Local Signal failure message and every ancestor up to the dialog also have no live/status/alert semantics. Focus moves to `Try again`, but that button has no `aria-describedby`, so its accessible name does not communicate that submission failed or that the draft was preserved.
- The Local Signal submitted and duplicate outcomes use the same presentation-only `InlineNotice` pattern. Sighted users receive a clear color/icon/text result; a screen-reader user is not guaranteed an announcement or equivalent focus relationship.

**Impact**

A non-visual user can activate a request and receive silence at the exact transition that determines whether a Table was joined or whether a local contribution failed, succeeded, or was deduplicated. In the Table case the user's virtual position also collapses to the document body. The user must manually rediscover both the result and recovery action.

**Acceptance criteria**

1. Provide an appropriate persistent live region or call-site `role="alert"` / `role="status"` semantics for the dynamic Table and Local Signal outcomes; do not make every static `InlineNotice` globally live.
2. On failure, expose the complete failure/preservation copy in the accessibility tree and retain or deliberately move focus to a meaningful recovery control.
3. If focus moves to `Retry join preview`, `Try again`, or `Return to venue`, associate the relevant result text with the control or independently announce the result.
4. Verify failure, success, and duplicate transitions in both KO and EN at `360×800` and `1440×1000`, with no duplicate announcement.
5. Add browser assertions for live semantics, active element, and message/control relationship; keep Axe, keyboard trap, Escape, and no-overflow gates green.

### SLEEK-R3-D3-002 — Labs signer failure is not exposed as a status change

**Severity:** `S2`
**WCAG:** `4.1.3 Status Messages (AA)`
**Flow/checkpoints:** `FL-018 ERROR/RETRY`
**Code:** `k-tour-id-app/features/ondo/labs/labs-entry.tsx:135`–`:140`, `:242`–`:249`; presentation-only primitive at `k-tour-id-app/features/ondo/shared/ui/sheet.tsx:148`–`:150`

**Reproduction**

1. Open acknowledged Labs with `?qa=1&scenario=labs-wallet-fail` and wallet state `WAL-DISCONNECTED`.
2. Activate `Simulate signer connection` and wait for `WAL-FAILED`.
3. Inspect `The connection fixture did not complete. No real account was affected.`, its ancestors, and the active element.

**Observed evidence**

- The failure message and ancestors through the Labs main surface have `role=null`, `aria-live=null`, and no programmatic description relationship.
- The connecting control is replaced; focus falls to `BODY`. The new `Try again` action is neither focused nor associated with the failure copy.
- The adjacent Bridge failure/success/cancel implementations correctly use `role="alert"` or `role="status"`, showing that the signer outcome is an inconsistent omission rather than an intentional silent pattern.

**Impact**

A screen-reader user starts a simulated signer connection, loses the focused control, and receives no guaranteed announcement that it failed or that no real account was affected. The safety/truth qualification is therefore not equivalent across visual and non-visual use.

**Acceptance criteria**

1. Expose `WAL-FAILED` through an appropriate alert/status live region containing the complete failure and no-real-account-impact message.
2. Preserve focus or move it deliberately to `Try again`; associate the outcome copy if focus is the notification mechanism.
3. Verify KO and EN at `360×800` and `1440×1000`; ensure a single announcement and no stale announcement after retry/success.
4. Add an accessibility regression matching the existing semantically correct Bridge outcomes and retain the modal, keyboard, Axe, target-size, and overflow gates.
